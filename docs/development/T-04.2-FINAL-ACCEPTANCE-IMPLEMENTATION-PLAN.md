## 1. Explicit Owner decisions (2026-11-21)

**T-04.D-ORDER = A — Global queue:** An event generated by a handler is enqueued into the single global queue, not preferentially executed inside its parent's transaction. Each eligible event is selected by ascending `(scheduledTick, insertionSequence)`, including already-queued, newly generated, and overdue events. A causal chain **is not automatically one atomic transaction**. An event generated for a future tick must not execute early. Preserve original scheduled tick and sequence on deferral; do not renumber to force ordering.

**T-04.D-LAG = A — Discard excess whole-tick backlog:** In a single `advance(elapsedMs)`, execute at most configured `maxCatchUpTicks` fixed simulation ticks. After that call, discard all *remaining complete tick intervals* accumulated beyond the bound, retaining only a fractional tick remainder. No time-debt queue or newly configurable debt cap. During Pause, do not advance or accumulate game time. Keep `ticksPerSecond` and `maxCatchUpTicks` explicitly configurable; no product-default tick rate.

These choices resolve the two BLOCKED acceptance items in T-04.1. They do **not** approve any new gameplay, Recovery or checkpoint design.

## 3. Implementation A: global event ordering

1. **Change transaction membership only as necessary.** A handler's staged state/RNG changes and *all its enqueue operations* are atomic within the **single triggering event's transaction**. On successful commit, its newly generated events remain in the canonical queue. Do **not** immediately execute child events within the parent's transaction, even if already due. The scheduler then selects the globally earliest eligible event in its own transaction. A parent and child are separate transactions unless a separately approved explicit atomic-group contract exists; **do not invent one**.
2. Preserve speculative staging, immutable snapshots, ID/sequence allocation, handler reference isolation, typed failures, diagnostics, and fail-stop. If the handler fails or staged enqueue overflows/depth exceeds 32, roll back the *entire parent event transaction* including state, RNG, queued children, IDs and sequence. A later child transaction failure **must not retroactively undo an already committed parent**; recovery orchestration is out of scope.
3. Enqueued future events count toward queue capacity but consume **zero execution slots until their scheduled tick**. Enqueued due events consume an execution slot **only when the scheduler executes them**. Existing due events with an earlier ordering key always execute first.
4. Maintain hard cap **250 actually executed events per tick**, with event 251 deferred FIFO. Preserve fail-stop `EXECUTION_LIMIT` for any **explicitly defined indivisible transaction** requiring >250 executed events, if the implementation supports such a transaction. Do not keep a fictitious >250-child-chain transaction merely to satisfy a historical test: with Owner decision A, 251 causally related events across **separate transactions** are deferred normally, not automatically `EXECUTION_LIMIT`. If an explicit multi-event atomic transaction still exists and cannot fit the *remaining* budget, defer it as a whole without canonical mutations. If no such group exists in T-04, identify the formerly applicable test as superseded and record why; do not claim to have tested a nonexistent grouping API.
5. Maintain order for overdue events, ties, and newly generated events with scheduled ticks earlier/later than queued events. Never permit an event with scheduledTick > current scheduler tick to execute early. Keep current scheduler protection against reopening budget on repeated same-tick calls.
6. Update obsolete tests asserting `[parent, child, existing]` when the global key demands `[parent, existing, child]`; replace with affirmative assertions of the newly approved order. Update older 2-event causal-chain DEFERRED tests to reflect **separate** transactions. Retain tests for atomic rollback of a handler that enqueues multiple children, RNG/counter rollback, 4096 queue, depth 32, diagnostics, and replay.
7. Verify that a handler generating an event with scheduledTick in the past does not bypass queue ordering: it is inserted with its original key, and selected next if it is now earliest; already executed events cannot be undone. Do not invent a retroactive execution rule.

**Regression examples (test values only):**
- Parent `(1, seq0)`, existing `(2, seq1)`, generated `(3, seq2)`, scheduler at tick 3 => `parent, existing, generated`.
- Parent `(1, seq0)`, existing `(2, seq1)`, generated `(1, seq2)`, scheduler at tick 3 => `parent, generated, existing` (scheduled tick outranks insertion sequence).
- Parent `(1, seq0)`, existing `(1, seq1)`, generated `(1, seq2)` => `parent, existing, generated`.
- Parent at tick 1 generates child scheduled tick 3 => child not processed at tick 1 or 2.
- A parent enqueues multiple children then throws => no child, no RNG/state/ID/sequence mutation survives.
- 250 executed events and one generated due event => 251st waits for next tick with original metadata.
- Replay same input and test seed across multiple ticks => identical state and queue snapshots.

## 4. Implementation B: bounded catch-up without time debt

1. Retain fixed-step simulation, configurable tick duration, Pause and existing callback API. On `advance(elapsedMs)`, accumulate finite nonnegative elapsed time, execute up to `maxCatchUpTicks`, then remove any **whole tick intervals still left in the accumulator** and keep only the fractional remainder `0 <= remainder < tickDurationMs` (allowing a small documented floating-point tolerance).
2. Do not carry whole-tick debt into later `advance(0)` calls. In particular, a one-second lag at test-only 10 ticks/s with `maxCatchUpTicks=2` executes exactly two ticks, with no extra catch-up ticks on `advance(0)`.
3. Test fractional preservation: e.g. test-only 10 ticks/s, maxCatchUpTicks=2, `advance(350)` executes 2 ticks and preserves 50ms; a subsequent `advance(50)` executes 1 tick. Do not make 10 ticks/s or 2 catch-up ticks a product default.
4. Test sustained lag, repeated zero delta, regular small deltas, Pause/resume, Pause triggered inside a tick callback, invalid deltas, and deterministic tick numbering. Paused calls must not accumulate elapsed time. If Pause occurs inside callback, stop immediately; do not execute extra ticks or create hidden catch-up debt.
5. Avoid numerical instability for very large **finite** elapsedMs; no unbounded loops, NaN accumulator, or silent tick counter corruption. Do not introduce a new timing policy beyond the approved discard-whole-ticks rule.
